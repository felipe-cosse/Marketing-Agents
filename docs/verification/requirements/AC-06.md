# AC-06 complete public template contracts

Requirement: every template has valid input/output schemas, an allowlisted tool
set, and an approval policy.

Status: implemented and locally exercised. The final committed feature must
pass the declared gates and retain its tree-bound attestation before merge.

## Source-to-HTTP acceptance bridge

The new acceptance test constructs the ordinary
`create_app(Settings(_env_file=None, ...))` application and checks that its query
service is the production `LocalCatalogQueryService`. It does not inject a
compiler, static query service, projected document, policy, or response fixture.
HTTPX ASGI transport exercises the real local identity, read routes, compiler,
projection and error middleware without a TCP server.

A separate default compilation of the tracked source provides comparison data;
it is not passed into the app. The template list must contain the source's exact
36 unique ordered IDs. The journey fetches every corresponding detail endpoint,
not just a representative role. Public capability and approval-policy registries
must have the same unique source identities and catalog version/hash.

For every template, the returned input/output documents must equal the compiled
source documents and retain the exact template-and-direction `$id`, declared
Draft 2020-12 dialect, object shape, required fields, closed top-level object,
title and description. All 72 schema identities must be unique and every schema
must pass the JSON Schema meta-schema check. Representative valid inputs and
outputs are validated against the returned documents, including advisory fields
where required; extra input fields and incomplete outputs must be rejected.
These samples do not exhaust the schemas' entire input space.

Each nonempty, duplicate-free capability allowlist must resolve in order to the
same public registry entries and source effect/family/idempotency declarations.
Each detail's policy must match its template reference, public registry and full
compiled policy fields. Every write-capability template must expose mutating
classification and the human external-write approval policy with the approver
role. Read-only templates must expose a no-approval policy. Both classifications
must actually occur, avoiding a vacuous write-policy assertion.

## Fail-closed negative controls

Each case first compiles an untouched private catalog copy successfully, then
introduces one targeted defect on the Newsletter Subscriber contract:

- Input schema identity no longer matches its template and direction:
  `template-schema-identity`.
- Output summary loses its maximum string length: `schema-unbounded-string`.
- Capability allowlist references an absent capability: `broken-reference`.
- Capability allowlist is empty: `template-capabilities-empty`.
- Approval policy reference is absent: `broken-reference`.
- Existing write capability is assigned the read-only/no-approval policy:
  `unsafe-write-policy` and `template-write-approval`.

The default compiler must raise the case-specific diagnostic codes. Both the
real template-list route and the affected template-detail route must then return
the API-09 `catalog_unavailable` problem with status 503, no-store caching,
authorization variation and no ETag. Responses must not reflect the private
source path, schema/template filename, mutation marker or compiler diagnostic.
The successful all-template journey prevents an always-unavailable service from
satisfying these negative controls.

Tracked catalog files are never modified. No compiler override or relaxed
contract is used. These controls qualify the selected defects, not every
possible unsafe source mutation.

## Limits

This is tracked-source and in-process API acceptance. It does not qualify
browser presentation, deployed HTTP transport, persisted configuration changes,
real provider delivery or production identity. Exposing a valid policy is not
proof of runtime approval enforcement; separate acceptance requirements exercise
the dispatcher and exact-action approval boundary. Socket denial permits Unix
sockets for asyncio, with the normal repository network guard also active. CI
remains disabled; no remote result is claimed.
