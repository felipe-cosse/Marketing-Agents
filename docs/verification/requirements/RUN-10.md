# RUN-10 verification note

RUN-10 introduces an immutable, integrity-checked `AuthenticatedPrincipal` issued behind the infrastructure identity-adapter boundary. Its exact authentication methods distinguish a fixed local human, bearer-authenticated human, verified webhook service, and internal scheduler service. Authentication evidence carries an optional `SecretStr` bearer credential that is excluded from representation and replaced by a boolean in its safe snapshot. The concrete local adapter accepts only absent credentials and snapshots the fixed actor, roles, and scopes from frozen validated Settings after rechecking local mode, non-production, and a declarative loopback host. The test suite enforces that no production application module imports the private principal issuer outside the domain definition and infrastructure adapter.

FastAPI now has a narrow injectable identity dependency seam plus real `POST /api/v1/approvals/{approval_id}/approve` and `/reject` mutations. `create_app` preserves explicitly injected providers and decision executors even when they are falsey, or installs the settings-bound local provider. The identity dependency parses only one standard `Authorization: Bearer` credential and rejects malformed evidence plus bounded caller-supplied actor, user, role, scope, principal, authentication, remote-user, and forwarded identity assertions. Generic proxy metadata such as `Forwarded` and `X-Forwarded-For/Host/Proto` remains API-09 scope. Authentication failures are generic 401 responses, forged identity evidence receives 400, and route/request validation emits only a capped set of root locations and stable codes—never request values, validator context, or attacker-chosen field names.

Authorization is all-of and has no administrator bypass. An integrity-valid HUMAN must have the global `approver` role and `approvals:decide` scope plus every role and scope in the persisted request policy. The policy's `allow_self_approval` flag is applied to the persisted requester snapshot. Successful authorization returns only the minimum matched grants needed for that decision, excluding extra principal roles and scopes. Baseline human, role, and scope authorization runs before opening a unit of work, while stored-policy authorization runs before trusted clock or ID acquisition.

The route body is an extra-forbid DTO containing exact `expected_generation`, plan-defined `expected_payload_hash`, and an optional bounded `SecretStr` reason. Actor, roles, scopes, authentication, correlation, and decision are not body fields: the path fixes approve or reject, the route generates correlation, and it maps the payload hash into a server-built application command. Viewer, operator, local-admin-without-approver, service, and missing principals fail before the executor on both routes. A baseline approver still fails when the real service finds a missing stored-policy scope. The route rejects any executor result whose decision/status/action state, IDs, hashes, Run, actor, auth method, or correlation do not bind the exact path and command. Successful responses contain only approval, decision, action, and Run IDs plus approved/rejected status; they do not advertise unimplemented resource links or claim connector execution.

`ApprovalDecisionService` accepts the already server-authenticated principal and server-built command. It loads and validates the sealed request, requires the exact unique current leaf, loads the bound action, recomputes its exact action binding with constant-time digest comparison, applies exact expiry, and derives the actor, authentication method, minimum roles/scopes, decision ID, action version, reason code, and UTC time. The repository repeats full-plan, keyed-integrity, current-leaf, and optimistic action/request checks. Concurrent approve and reject calls at the same barrier yield exactly one decision, one request/action transition, and one pair of witnesses.

After the decision CAS and before a single commit, the service appends `action.approved` or `action.rejected` and `approval.approved` or `approval.rejected`. Both witnesses carry direct composite links to the same approval request and decision, while their audit actor and correlation values are pseudonymized from the same raw principal and correlation used by the decision. The event factory rejects proposal, delivery, terminal-reason, authority, context, or lifecycle drift. An injected failure after both audit drafts are appended rolls back the decision row, request transition, action transition, and audit rows. Corrupt request/action hydration is mapped to stable non-sensitive service errors, and replay of a decided request never fills a deliberately removed audit witness. No decision creates a reservation, attempt, receipt, connector call, write proof, or parent Run/step release.

Machine authority: `RUN-10.json`. The evidence deliberately does not claim authenticated provenance for the pre-existing free-string `EffectPlanRequest.requested_by`; the self-approval rule currently compares against that stored snapshot only. It also does not claim approval creation/list/detail/full projections, shared correlation middleware, the complete problem-details contract, production executor composition, production bearer/webhook/scheduler providers, canonical listener bind, trusted proxy enforcement, CSRF/Origin/Fetch-Metadata defenses, approval-use consumption, complete-set barrier release, connector authority, or PostgreSQL runtime race execution. API-06 owns the broader approval API and error/correlation composition, the planning/intake boundary must issue authenticated requester provenance, API-06/API-09 own browser mutation and proxy/bind protections, ORCH-08 owns release and reservation, and the PostgreSQL environment owns runtime parity.
