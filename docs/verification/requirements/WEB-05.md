# WEB-05 verification

WEB-05 adds a real `/approvals` route and pending-count navigation badge. The queue requests pending approvals by default and preserves API keyset pagination. Status is a server query; department and action type are explicitly labeled as filters over pages already loaded in the browser. Empty results, truncation, loading, unavailable data, and exact versus lower-bound badge counts remain distinguishable. The browser never places a redacted payload, payload hash, or decision reason in URL state, storage, cookies, or query keys.

List and detail responses cross an endpoint-specific fail-closed boundary. The client accepts only the exact API-06 snake-case projections, stable same-origin resource links, complete domain lifecycle tuples, nanosecond-precise UTC ordering, lowercase SHA-256 hashes, ordered pages, bounded cursors, and recursively bounded JSON-safe redacted payloads. Unknown fields, unsafe object keys, cycles, sparse arrays, over-budget data, mismatched IDs or links, inconsistent actionability, self-renewal, invalid decision/use timing, and decision drift are rejected before rendering.

Selecting a row loads the exact approval separately and shows action type, destination summary, payload hash, server-provided redacted payload, requesting instance, run, authoritative timeline, step, external-action/receipt resource, expiry, status, and one-time state. The approve/reject dialog repeats that immutable action, focuses Cancel first, traps focus, restores a viable opener or the review-panel fallback, and closes on Escape while idle. Expired, already decided, consumed, superseded, and server-declared nonactionable requests expose a concrete disabled reason. A scheduled local clock disables a pending decision as soon as its authoritative expiry arrives, and the click handler rechecks the current time before issuing a request.

A decision sends exactly `expected_generation` and `expected_payload_hash` through the existing memory-only local-session CSRF boundary. One `csrf_token_invalid` response may refresh the token and replay the identical serialized body; no other failure is automatically retried. The client cross-binds the response to approval, action, run, decision kind, generation, hash, and `Location`, then refetches the authoritative detail before saying `Approval recorded`. A `409` is presented as a conflict after an attempted authoritative refetch. Neither path claims that a connector executed, delivered, published, or completed the action.

For Email, the page issues a bounded all-status query for the selected run and shows the `newsletter.subscribe` and `crm.upsert-contact` approvals separately, including the one-approved/one-pending state. The zero-call message is rendered only when that page is complete and the strict API-07 run projection confirms mock execution, an approval-required run still awaiting approval, exact approval/action/step/type/status/request/expiry bindings, at least one live pending request, zero `delivery_attempt_count` values, and absent receipt, result, and completion facts. A scheduled clock ages this proof out at the first approval expiry. Any nonzero attempt, partial page or set, mismatch, expiry, terminal action, malformed contract, or unavailable summary yields an explicit unavailable state rather than an inference.

The focused unit gate covers 34 API, parser, mutation, query, dialog, queue, conflict, lifecycle, expiry, and negative-evidence cases. The dependency-free witness executes the production approval and run-safety normalizers plus the real CSRF mutation boundary under pinned Node 24.20.0. The browser gate rebuilds the production Vite application, uses loopback-only same-origin fixtures over the real base hierarchy boundary, exercises navigation, pending/all/filter behavior, the run-scoped two-action Email proof, exact detail/dialog content and resource links, keyboard focus, exact CSRF body and header, an injected `409`, a coherent concurrent approval that retains immutable request identity, private-decision-reason storage secrecy, and zero external requests.

WEB-06 remains responsible for a dedicated in-app run timeline and artifact/receipt viewer; WEB-05 provides direct authoritative API resource links. WEB-07 and WEB-08 retain narrow semantic-tree and exhaustive accessibility acceptance. DEL-05 retains default backend service composition, so the browser gate supplies deterministic same-origin session, approval, conflict, and safe run-summary fixtures without weakening production client validation.
