# SCHED-06 — Restart-safe due-schedule recovery

SCHED-06 composes the existing scheduler contracts into a restart path without weakening any fence. A claim abandoned before processing remains active through its exact expiry instant. Only a strictly later injected UTC instant lets another worker replace it, and the replacement retains the original schedule ID, persisted due instant, and recurrence-semantics version while receiving a new owner/version fence. Processing that replacement then uses the SCHED-04 plan and SCHED-05 transaction to persist one `run_once` or `skip` outcome, advance the next UTC occurrence, and clear the replacement lease.

File-backed SQLite restart tests close and reopen the database around the abandoned claim. A synchronized two-session race proves that only one restarted worker acquires the expired due instant. A separate fault first rolls back the entire processing transaction and then proves that strict-expiry recovery creates exactly one occurrence and, for `run_once`, one WorkItem, primary Run, initial transition, `run.received` audit, occurrence audit, and next-occurrence audit. Recovered `skip` instead persists one skipped occurrence and the next time without WorkItem or Run.

Response loss after a successful commit follows a deliberately read-only path. Both scheduler mutation witnesses carry the same domain-separated fingerprint over every immutable claim coordinate: schedule and due identity, lease owner, claim and expiry times, recurrence version, and fencing version. The service reconstructs the deterministic claim-time plan and requires that fingerprint, the exact current schedule projection, stable occurrence identity and state, complete WorkItem/Run links when work was admitted, keyed admission facts, first Run transition, `run.received` event, scheduler occurrence event, and `schedule.next_occurrence_persisted` event. Concurrent retries return `DUPLICATE_SUPPRESSED` while a test unit of work forbids commit, the clock and ID source are unusable, and byte-for-byte schedule and audit snapshots plus all row counts remain unchanged. Changed payload, mode, configuration, claim time, or lease expiry is rejected, and a missing advancement audit fails as an incomplete committed outcome without recreating the witness.

Replay revalidates current catalog policy but preserves the original historical receipt. A compatible catalog-hash change therefore still returns the same WorkItem and Run with the Run's original catalog hash; it does not rewrite receipt history to the newer release.

`DUPLICATE_SUPPRESSED` is an application disposition, not a newly appended `schedule.duplicate_suppressed` audit event. This keeps committed replay observational and race-free while requiring the original globally ordered mutation witnesses to remain intact. Plan 08's operational `schedule.claimed`, `schedule.lease_conflict`, and `schedule.duplicate_suppressed` events remain later scheduler-worker and observability work; this evidence does not claim them.

The proof is for one durable scheduler occurrence and one idempotent WorkItem/primary-Run receipt, not exactly-once Run execution or downstream effects. It covers the exact immediately committed schedule projection at `claim.version + 1`; it does not reinterpret an older occurrence after later schedule cycles. Runtime evidence uses independent file-backed SQLite sessions and injected clocks without sleeps. PostgreSQL runtime contention, polling/CLI loops, metrics, APIs, authorization, migrations, deployment, and clean-start packaging remain outside scope, and AC-12 retains end-to-end scheduler-to-Run-worker acceptance.
