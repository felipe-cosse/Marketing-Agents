# AC-14 — Complete and transactional public audit timelines

Status: verified by composed local acceptance and focused regression checks;
exact committed-tree gates and the source-restoration witness required before merge.

Requirement: `Every transition and approval appears in audit timeline.`

## Contract and discovered implementation gap

Plans 04, 05 and 13 require same-transaction business mutations and audit events,
monotonic per-run order, stable public pagination, safe actor/correlation and
resource links, and retained event skeletons when optional metadata expires.
An audit-row-to-timeline comparison alone cannot establish completeness: the
same missing business mutation could be absent from both.

Inspection found one actual missing-audit path. `RunWorker._fail` invoked
`TerminalExecutionCleanupService.fail_execution_in_uow` and committed the staged
Run/Step/action changes, but discarded the returned audit drafts. Unlike the
other cleanup callers, it never appended those drafts. The repair retains the
cleanup result and appends its events before the existing unit-of-work commit.
Worker ownership fencing, cleanup policy, dispatch authority and error
classification are unchanged. An audit append failure now rolls back that
cleanup transaction as required.

## Independent completeness evidence

The composed journeys use fresh migrated and seeded file-backed SQLite, default
runtime composition, public admission/approval routes, real `RunWorker` execution,
and the original deterministic adapters. READ completion, approved Email
completion, rejection, and expired/replaced approval generations are checked.

The oracle starts with independently persisted business facts: Run/Step
transition rows, approval requests/decisions/uses, attempts, receipts and artifacts.
It joins those facts to the exact corresponding durable events, including
identity, mutation version, state, sequence, actor/correlation and timestamps.
Run/Step version and state chains must account for every persisted aggregate
version, so a change missing from both the transition and audit tables cannot
satisfy the oracle. Decision actors are checked against the known local human
principal and correlation returned by the public command, not only against the
decision row being tested.
Then it joins those events to small-page public run timelines and the global
audit feed. Equal timestamps cannot substitute for sequence ordering. Runtime
reconstruction and cursor continuation cannot drop or duplicate entries.

The unexpected-worker-error journey enters the real released Email dispatcher
and injects an exception before any provider call. It must leave one failed Run,
one failed step, two skipped steps and two cancelled actions, with exactly six
new cleanup audits. Every persisted Run/Step transition has its exact event;
each cancelled action has its own state/version witness. The already-consumed
approval authority is unchanged. The public timeline exposes the durable
failure facts without the injected private exception text. Reconstructing the
runtime and advancing beyond claim cooldown produces no further work or audits.

## Atomic failure and retry evidence

Five public-command cases exercise first approval, final approval/all-action
release, queued cancellation, pre-barrier cancellation and cancellation after
release but before a connector call.

Their fault seam calls the original audit append method and allows its real
flush to finish, then reads the staged business mutations and both run/feed
sequence counters in that same transaction before raising. A fresh session must
then see an exact match with every pre-command ORM table, with no exclusions.
This rules out a passing test caused by failing before anything was staged.
Restoring the append method and retrying the same public command succeeds once,
with the same ordered mutation facts and contiguous sequences. Reconstruction
preserves those committed rows. These command journeys make no provider calls.

The worker-failure case additionally injects a failure after all six cleanup
audits have flushed. It checks the staged terminal states and both counters,
then exact rollback of business/audit/allocator state. Worker lease/session
bookkeeping is deliberately excluded from this worker snapshot, unlike the
all-table public-command snapshots. A later claimed retry produces one complete
terminal outcome and cannot consume approval authority again.

## Public projection boundaries

The global audit feed binds each cursor to its original high watermark and
filters. A genuine approval committed between page requests is absent from the
old snapshot and present in a new one, even with identical timestamps. Changing
the cursor's filter fails closed. The run timeline is ascending per-run sequence
pagination; it does not promise a fixed high watermark.

Immediately before audit metadata expiry, full allowlisted metadata is visible.
At the exact expiry boundary, a reconstructed runtime hides only metadata and
sets `metadata_expired`. Every other public field remains exactly unchanged:
event identity/order/type, transition states, decision identity where exposed,
actor/authentication/correlation, timestamps and resource links. Durable audit
rows are unchanged by these reads. This proves projection expiry and skeleton
visibility, not physical deletion or a retention-maintenance sweep.

## Verification protocol

Preflight checks completed during implementation:

- Four completeness journeys, including independent response-derived approval
  authority expectations, passed together in 41.02 seconds.
- 130 existing lifecycle, approval, audit persistence, public API and redaction
  cases passed together in 31.13 seconds.
- Five public-command post-flush rollback cases passed in 50.60 seconds.
- Two public pagination/expiry cases passed in 17.68 seconds.
- Two worker-failure cases and 14 existing DEL-05 worker/ownership regressions
  passed together in 96.51 seconds. The later source-bound worker gate passed
  both cases again in 21.49 seconds.
- Complete source typing passed for 285 files; architectural boundaries and
  scoped Ruff formatting/lint passed.

These are separate, potentially overlapping runs, not a unique test count.

`AC-14.json` declares ten exact-tree gates covering composed completeness and
projection; public-command rollback; unexpected-worker failure; lifecycle and
approval audit regressions; public audit/redaction regressions; existing worker
ownership and AC-13 cancellation journeys; complete source typing; architectural
boundaries; scoped formatting; and lint.

The connection witness restores only `workers/runtime/run_loop.py` to its base
version in an isolated copy and requires the new worker-failure gate to fail.
This checks that the regression suite is connected to the repaired behavior,
not merely a pre-existing passing test.
The worker gate uses pytest's `pythonpath` override to prepend the current tree's
source directory before collection, and the test asserts the worker module's
source path. Otherwise the development environment's editable installation could
import the original worktree instead of the isolated base-restored copy.

After preflight verification, the single requirement feature commit must pass
all manifest gates and the connection witness on its exact tree. Its
non-fast-forward merge must have that identical tree. Composed acceptance and
repository history checks are rerun after the merge. Neither the evidence
verifier nor the history policy is relaxed.

## Limits

Tests exercise SQLite and deterministic local mock effects through in-process
ASGI/runtime composition. They do not qualify live providers, PostgreSQL races,
OS-process crashes, distributed durability or deployment. New composed journeys
cover the stated concrete paths; existing focused lifecycle, audit, concurrency,
approval and redaction gates supply additional evidence, not an exhaustive proof
of every possible workflow interleaving.

The run timeline is intentionally a smaller projection than the global feed;
the latter additionally exposes exact decision/attempt/mutation links. Audit
append-only product APIs and integrity checks are not cryptographic tamper proof.
Direct local database administrators remain trusted. Python sockets are denied
except local Unix sockets in every pytest gate. CI remains disabled.
