# AC-02 exact catalog API inventory

Requirement: the catalog API exposes exactly 5 departments, 12 functions,
36 reusable templates and 43 deployed instances.

Status: implemented and locally exercised. The final committed feature must
pass the declared gates and retain its tree-bound attestation before merge.

## Acceptance boundary

The AC-02 test constructs the normal `create_app(Settings(...))` application and
asserts that it selects the production `LocalCatalogQueryService`. It does not
inject projected documents, a static query executor, a replacement compiler, or
an API response fixture. HTTPX ASGI transport exercises the real routes, local
identity, catalog loading, validation, projection, and response middleware in
process without a TCP listener.

The positive journey reads `/api/v1/catalog`, `/api/v1/catalog/hierarchy`,
`/api/v1/agent-templates`, and `/api/v1/agent-instances`. It checks actual array
lengths and unique IDs as well as advertised counts; ordered departments,
functions, templates and instances agree across the aggregate, nested hierarchy
and list projections. The instance-to-template pairs also agree across the
aggregate, hierarchy and dedicated instance list, all 36 templates
are represented, and content version/hash match the tracked v1 release.

The negative control removes one valid Community deployment only from a private
catalog copy. All four routes must reject that incomplete source using the real
compiler and sanitized `application/problem+json` error boundary, with no-store
responses and no reflected source filename, removed ID or compiler diagnostic.
The positive journey prevents an always-unavailable API from satisfying the
negative test.
