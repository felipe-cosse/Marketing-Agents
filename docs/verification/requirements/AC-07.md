# AC-07 five provenance-linked local demos

Requirement: five valid provenance-linked demos; writes wait and execute only
after exact approval.

Status: implemented and locally exercised. The final committed feature must
pass every declared gate and retain its matching tree-bound attestation before
merge.

## Real local composition

The acceptance journey uses a fresh file-backed SQLite installation, the shared
digest-key initializer, real migrations and catalog seed, `build_runtime`, the
ordinary FastAPI application, and `RunWorker`. HTTP requests use in-process ASGI
transport and the real same-origin session/CSRF helper. Only time is controlled.
Call observers record entry into the real deterministic model and registered
connector methods, then invoke those original methods; they do not supply
responses or replace the production runtime with a fake service.

Each of the four read-only scenarios is admitted through its public demo route,
survives runtime reconstruction before execution, and completes through the
worker. Its versioned input and output schemas, selected instances, producing
step, attempt, state path, call counts and persisted artifact lineage are
checked. A completed run survives a second reconstruction without another call
or artifact. The Email journey exercises the same default composition and
retains its approval boundary across restart.

## Provenance and representations

Artifact identity joins to the persisted WorkItem, Run, plan, producing step and
successful model attempt. Assertions check the admitted-input digest, input
source, template/instance/configuration identity, output schema identity/version
and hash, payload hash, timestamp and sensitivity classification. Catalog
version is recovered from the persisted catalog-release row identified by the
artifact's exact catalog hash; it is not inferred from an unrelated current
catalog version.

The artifact's `providers` field records its direct deterministic LLM producer.
Email's two ordered mock receipt references additionally join through exact
external actions and durable connector receipts to their connector name, mode
and implementation version. Those values are recorded at receipt creation from
trusted mock implementation metadata, not model output or a later registry.
The mock binding registry uses the same implementation-version constant.

Email retains the established single `email_onboarding_summary` envelope. Its
closed, versioned output schema contains a nested `welcome_message_draft` with
draft-only/not-sent status. The envelope's schema hash and payload hash cover
that nested content. It is not a separately addressable persisted artifact and
does not create an invented parent-artifact edge. No email is sent.

## Exact all-approvals barrier

The Email run first reaches `awaiting_approval` with two distinct action-bound
approval requests, no model/connector entries, no execution attempts, no
receipts and no artifacts. An incorrect expected hash is rejected without
releasing work. One exact approval followed by a worker drain still leaves both
writes and the model at zero. The second exact approval transitions the run to
execution, but the HTTP decision handler performs no inline dispatch.

After runtime reconstruction, the worker invokes each exact approved write once
and generates one welcome draft. The test joins requests, decisions, consumed
uses, reservations, action hashes, bindings, idempotency keys, dispatch attempts,
durable receipts and summary references. The two successful connector effects
are mock-only. A completed-run restart adds neither a call nor an artifact.

## Durable connector-version repair

Before AC-07, mock receipts preserved action/capability identity but did not
preserve connector implementation versions. The repair records connector
identity before the durable receipt is inserted. It does not change action
hashes or idempotency keys and does not require a database migration.

Replay preserves the original receipt identity and metadata, including its
historical version. Exact legacy receipts without version information remain
explicitly legacy; they are not relabeled with today's version. Replay must
still validate exact action scope and deterministic receipt/status/static
metadata. The repository's strict full-result collision checks remain intact.

## Limits

These are local deterministic mock and in-process API results, not browser,
live-provider, cloud-delivery or production-identity evidence. The connector
version assertions describe newly created versioned receipts; old unversioned
receipts cannot establish a historical implementation version. The nested
welcome draft has no separate artifact resource. Existing demo suites supply
determinism and negative controls beyond the new cross-composition journeys.
The pytest processes deny network sockets except Unix sockets needed by local
asyncio. The process-composition regression also starts a fresh worker child
configured mock/offline with external-network opt-in disabled; the parent's
monkeypatch-based guards do not themselves sandbox that child. Accordingly,
the full regression gate is labeled `not_enforced`, not OS-isolated. This is
not a substitute for the separate AC-15 network-isolation qualification. CI
remains disabled, and no GitHub workflow result or remote publication is claimed.
