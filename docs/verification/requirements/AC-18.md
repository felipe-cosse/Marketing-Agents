## Ported behavior and limits

The current collector retains its 26 authoritative counters. Nine fixed control
read sites append three diagnostic bins each: exact signed 64-bit EFAULT, another
nonzero helper result, or pointer wrap detected before the helper. The sites are
`prctl_args`, `seccomp_args`, `vma_name`, `action_value`, `exit_syscall`,
`exit_result`, `notify_sizes`, `vma_exit_syscall` and `vma_exit_result`.
Every failed read contributes exactly one bin and one existing
`control_read_error`; their totals must agree. Reject malformed or incompatible
counter evidence rather than silently discarding appended fields.

The original network bytecode and all authoritative classifications remain
unchanged. Read sizes, pending-map cleanup, filter-installation rejection,
source/ABI/cgroup qualification and the production disabled-VMA full-width
native EINVAL requirement are preserved. Diagnostic accounting cannot excuse a
read failure, turn an unknown into a permitted call, or count a rejection twice.
No names, user labels, memory addresses, buffer bytes, raw helper returns or
unrestricted exception text are retained.

The standalone VMA runner compares untouched, pre-read and inaccessible owned
mappings using the current collector and bounded live kernel configuration.
It requires a clean exact source commit and a previously acquired matching
immutable image. It is native ARM64-only, creates fresh owned targets, preserves
existing network-none/container boundaries and performs bounded owned cleanup.
Unsupported execution, missing configuration and incomplete evidence fail.
Completing all diagnostic probes is not a passing acceptance result:
`diagnostic_completed` and successful cleanup are separate from the report's
false acceptance status. The production four-suite inventory does not invoke
this experiment or gain a diagnostic exception.

This is supplementary troubleshooting evidence, not universal memory-race
protection, whole-binary provenance, production-provider qualification or
adversarial Docker-administrator isolation.

## Approved registry validation optimization

One measured registry build made 152 schema compilations for 82 exact canonical
content/expected-identity pairs. The approved optimization reuses only a
successful schema-structure check for the same freshly canonicalized bytes and
expected schema identity during one owned registry build. Each compilation still
checks identity, dialect and local references and creates a fresh validator;
every workflow and payload check remains in place. Standalone compilation stays
fully checked. Successful results are not shared across registry builds, and
the scope is discarded on normal return or failure. No catalog or database
reflection is reused and no process-global validation cache is introduced.

Regressions cover changed content under the same ID, changed expected identity,
invalid definitions, local-reference and dialect restrictions, non-caching of
failures, scope teardown and rebuild freshness, fresh validators and unchanged
workflow definitions and hashes. This is a bounded CPU optimization, not a claim
that the full backend deadline will now pass. All complete qualification must
run again against the revised frozen candidate.
