# AC-08 — Mutating actions cannot cross the approval boundary

Status: verified by executable local acceptance and contract checks.

Requirement: `Mutating action cannot cross approval boundary.`
The source contract is plan 06, especially the all-approvals barrier, atomic
release, individual dispatch claim, and exact mock authorization sections.

## New evidence

`tests/acceptance/test_ac_08_dispatch_approval_boundary.py` starts from a fresh
migrated and seeded SQLite installation and uses the default runtime, real
session/CSRF-aware API, real worker, production dispatcher, registry gateway,
and durable connector mock bundle. The AC-07 setup and observation helpers are
reused without replacement responses or repositories.

The journey proves:

1. Real Email admission/planning creates exactly two registered write actions
   and their matching write steps and pending approval requests. The gateway's
   current delivery contracts equal the persisted snapshots, and exact request
   types accept the proposed command payloads.
2. Direct calls to those real mock handlers with valid commands but missing or
   unsealed authorization fail with `authorization_mismatch` before any ledger
   effect. These are deliberate handler invocations; the zero-call assertions
   below count dispatch gateway/model/read-adapter invocations, not these
   rejected attempts to enter the inner handler boundary.
3. Active production dispatcher calls using both valid persisted action IDs
   fail with `action_not_dispatchable` when neither approval is present. Run,
   step, action and approval snapshots remain identical; no committed release
   authority, use, reservation, dispatch/execution attempt, receipt, artifact,
   or gateway/model/read call is created. Execution-control model/tool call
   counts remain zero.
4. After the first real HTTP approval, both IDs remain non-dispatchable,
   including the individually approved action. All preceding zero-effect and
   unchanged-snapshot assertions still hold.
5. Final exact HTTP approval consumes and reserves the complete set atomically,
   makes the run executing and write steps ready, and performs no inline dispatch.
6. The same dispatcher, gateway, mock bundle and action IDs then succeed. Sealed
   proofs join exactly to action/envelope/hash/request/decision/use/reservation/
   idempotency identity and authoritative durable receipts. There are exactly
   two successful first dispatch attempts and two mock ledger inserts.
7. A real worker finishes the same workflow with one welcome-draft model call,
   both actions succeeded, and no additional write. Early denied attempts have
   not poisoned or permanently disabled legitimate execution.

`tests/contract/test_ac_08_all_write_authorization.py` independently pins an
eight-operation payload fixture inventory equal to both catalog and registry
WRITE inventories. It resolves actual shipped methods, including disabled ones,
and validates commands with their exact registered request classes.

| Operation | Expected valid-proof behavior |
|---|---|
| Newsletter subscribe | One mock ledger effect |
| Newsletter unsubscribe | One mock ledger effect |
| CRM upsert contact | One mock ledger effect |
| Events enroll attendee | One mock ledger effect |
| Community send message | One mock ledger effect |
| Community share material | One mock ledger effect |
| Email send message | Disabled; absent from binding handlers; zero effects |
| Spreadsheet update rows | Disabled; absent from binding handlers; zero effects |

For every case, forged proof construction fails. The actual handler rejects
`None`, an arbitrary object, and the raw canonical envelope without ledger effects.
A genuine proof also cannot authorize a changed, still schema-valid typed command.
Six enabled methods report `authorization_mismatch`; the two disabled methods
report `operation_disabled` even with valid proof. Enabled positive controls then
produce a matching mock capability/family receipt and exactly one effect.

The connector matrix uses synthetic trusted reservations to isolate the inner
proof contract. It does not claim eight persisted human-approval journeys: the
real Email journey proves the shared outer approval/dispatcher boundary.

## Scope and limits

This requirement adds acceptance coverage and evidence, not application changes.
The previous family-named SAFE-02 fixture is not treated as actual-handler
coverage; the new matrix invokes every real registered write method.

All pytest gates run in-process with sockets denied except local Unix sockets.
The HTTP transport is in-process ASGI; provider outcomes and side effects are
deterministic local mocks. No browser, cloud/provider delivery, arbitrary-code
security boundary, or universal distributed exactly-once claim is made.

Social publishing, CMS mutation and fulfillment creation remain absent from v1;
ARCH-07 tests their absence rather than enabling them. Expired, reused and changed
stored approval proposals are AC-09's separate acceptance scope. Existing exact
payload/scope regression checks remain required here. CI remains disabled.
