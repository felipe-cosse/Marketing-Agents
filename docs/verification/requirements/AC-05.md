# AC-05 stable unique instance identities

Requirement: stable instance IDs are unique.

Status: implemented and locally exercised. The final committed feature must
pass the declared gates and retain its tree-bound attestation before merge.

## Full inventory authority

The AC-05 acceptance journey compiles the tracked v1 catalog through the default
production compiler. Its expected inventory is independently specified from plan
02: an explicit ordered table contains every one of the 36 template IDs and its
allowed source ordinals. Replacing `tpl.` with `inst.` and appending each listed
ordinal produces the full 43 expected IDs, not merely an arithmetic total or an
expectation derived from compiler output.

The comparison pins every `(instance ID, template ID, source ordinal)` tuple in
order. All 43 IDs must be unique. Non-Community roles have only `.01`; each of
the seven Community roles has both `.01` and `.02`. This verifies the complete
identity inventory rather than sampling one department or asserting count alone.

## Configuration stability

A private source copy changes the LinkedIn Post Drafter instance's enabled flag
to false and its configuration revision to 2. The production result must contain
those changes and a different semantic content hash, while preserving every
ordered instance ID against both the baseline and the independent expected list.
The changed fields and hash prevent an ignored mutation from appearing stable.

This case is deliberately limited to source-default configuration changes. It
does not claim live database/API configuration or restart coverage, nor does it
test every mutable deployment field named in the broader plan.

## Identity-specific negative controls

Each mutation is made only in a private catalog copy and is submitted to the
unmodified default compiler:

- Appending a duplicate deployment requires both `duplicate-id` and
  `duplicate-instance-id`. The fixture also changes the total to 44; a generic
  global count failure alone cannot satisfy these assertions.
- Moving an instance ID to a syntactically valid Blog namespace while retaining
  its Social template reference requires `instance-id-template-mismatch` and
  `instance-template-identity`.
- Replacing a non-Community `.01` ID with `.02` and matching source-ordinal
  metadata requires `deployment-ordinal` and `instance-source-ordinal`. This is
  a forbidden deployment ordinal, not just an ID/metadata disagreement.

The compiler may emit additional relevant diagnostics; the test requires the
specific identity codes without depending on the complete diagnostic ordering.
Namespace and ordinal mutations preserve the source record count. No mocked
compiler or weakened catalog contract participates in AC-05 acceptance.

## Limits

This is a local source-to-compiler acceptance journey, not HTTP, browser,
database, real-provider or production-identity verification. The repository-wide
pytest external-network guard remains active. CI remains disabled at user
direction; no remote publication or workflow result is claimed. The recorded
preflight is not a substitute for final committed-tree verification.
