# RUN-08 verification note

RUN-08 now provides one canonical durable approval request and lifecycle wrapper, an append-only decision fact, and a typed future-use fact. Each request binds the exact immutable external action, authorization-set ID, set-level `proposal_revision`, Run, plan, runtime step, semantic and exact action hashes, connector/binding facts, policy snapshot, requester snapshot, requested/expiry times, safe destination, and redacted payload projection. Expiry is exactly the snapshotted policy TTL. Purpose-specific, domain-separated keyed HMAC digests cover every request leaf and lifecycle scalar, every decision actor/authentication/scope/reason/time fact, and every use/reservation/time fact; raw records are verified before approval domain hydration, and legitimate lifecycle CAS updates reseal the request atomically. Repository hydration also revalidates the complete persisted ORCH-09 plan and RUN-05 action aggregate, recomputes the only permitted projection from the action envelope and sealed RunStep redaction fields, and checks current request/action lifecycle and complete WRITE-step membership. Wrong-key restart, requester or decision rewrites, coordinated renewal-time shifts, string-to-boolean coercion, forged idempotency state, raw projection canaries, partial sets, generation gaps, action-version drift, and contradictory request/action states fail closed with sanitized persistence errors.

`ApprovalRecordService` composes RUN-05 action registration with generation-one approval storage for an already-persisted validated write plan. A new complete set creates all proposed actions, atomically advances every member to `AWAITING_APPROVAL`, inserts all requests, and appends `action.proposed`, `action.awaiting_approval`, and `approval.requested` witnesses in the same outer unit of work. Replay reconciles regenerated planner IDs, authorization-set IDs, runtime-step IDs, and request times by stable step/action semantics, then returns the original stored action/request identities and times. It validates the complete per-Run audit timeline and exact mutation witnesses and never fills a partial action/request set or missing audit history.

The approval repository supplies a one-winner decision CAS foundation. It validates the exact request, policy roles/scopes, self-decision rule, decision time, and action version before inserting a decision and advancing the bound action to `APPROVED` or `REJECTED`. This is deliberately not a public authorized-decision endpoint: RUN-10 and API-06 must provide the authenticated server principal, trusted clock, and decision/action audit composition.

Public expiry and renewal operations use both request and action optimistic fences. PENDING or APPROVED requests may expire only at or after their immutable expiry; an approved action reopens to `AWAITING_APPROVAL` in the same transaction. Renewal may replace only that one expired leaf while every action, set, plan, revision, step, connector, policy, projection, and requester field remains unchanged. The old request links exactly one generation-plus-one replacement, response-loss replay returns the stored replacement, and a later decision on that replacement does not invalidate historical expiry/reopen audit verification. File-backed SQLite races prove one audited service winner without raw `OperationalError`, while audit faults roll back both request and real APPROVED-to-AWAITING action changes.

`ApprovalUse` remains a storage contract for ORCH-08 rather than a public mutation. Its composite foreign keys and hydration bind the approved decision, request, action, set, Run, plan, revision, step, reservation ID, and exact reservation/use time. Cross-scope, time, or contradictory post-consumption action-state corruption is rejected. SQLite creates the complete schema with an exact boolean constraint, and every mapped table compiles for PostgreSQL.

The corrected replacement boundary is explicit: `proposal_revision` belongs to the whole authorization set. Expiry may renew a leaf only for the same exact action/set/epoch. Any semantic, membership, or plan change returns `full_set_epoch_required`; ORCH-08 must introduce the authorization-set head and atomically create new identities for every sibling before superseding the entire old epoch. RUN-08 does not persist or select mixed per-step semantic revisions.

Machine authority: `RUN-08.json`. The evidence intentionally does not claim authenticated requester/actor provenance, a public decision endpoint, approved/rejected decision audits, one-time barrier release, use insertion, full-set head/supersession, active parent Run/cancellation fencing, atomic write-plan activation through ORCH-09, API presentation, migrations, key distribution/rotation, or PostgreSQL runtime race execution. Deployment must inject the configured restart-stable root `DigestKey`; fixed approval-request, decision, and use HMAC domains are distinct from the admission-digest domains. Configuration and DEL-04 own key provisioning and rotation. These digests detect persisted corruption but do not authenticate the stored principals. The remaining boundaries belong to RUN-10/API-06, ORCH-08, API-07, DEL-04, and the PostgreSQL integration environment respectively.
