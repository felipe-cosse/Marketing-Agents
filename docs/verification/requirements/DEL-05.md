# DEL-05 local startup verification

DEL-05 composes the existing deterministic services into independently supervised
API, run-worker, scheduler-worker, and web processes. `make up` builds from frozen
locks, initializes a private database/key pair, migrates and seeds it, waits for
health, and publishes one loopback URL. No provider credential or `.env` is needed.
See [local operations](../../local-operations.md) for startup, native development,
paired backup/recovery, and the explicit single-operator trust boundary.

## Implementation boundaries

- Frozen additive revision `0006` adds a dedicated run-claim table. Previous
  migrations remain unchanged. Claims use owner/token/version fencing, bounded
  batches, lease renewal/expiry, and bounded graceful shutdown.
  Failure handling locks and validates the current claim in the same transaction
  as lifecycle/step/audit mutation; a resumed stale worker cannot fail its
  successor's run. Replaced, expired, and current-owner cases cover both branches.
- Workers reuse the existing intake, lifecycle, planning, approval, and durable
  dispatch services. Only the five implemented demo workflows execute. Unsupported
  workflows terminate honestly; generic webhook/schedule fixtures prove admission
  and replay, not arbitrary workflow execution.
- Backend containers have `network_mode: none`. The API listens on an owned,
  private Unix socket, shared only with the web proxy through a third IPC volume.
  The socket directory is `0750`, socket `0660`; stale-path replacement requires
  ownership, type, inactivity, and unchanged inode checks. Shutdown removes only
  the process's own socket.
- API/workers mount the digest key read-only. Read-only initialization explicitly
  defers the SQLite fingerprint query to the following writable migration owner,
  which checks pairing before schema/data writes. This avoids read-only SQLite
  WAL/SHM initialization errors without accepting a mismatched or replacement key.
- Native supervision validates pinned tools, private state, ports, and health;
  it owns only its process groups. Fresh startup and restart preserve the same key.
- Backup uses SQLite's online snapshot API, not a live database-file copy. A
  verified checksummed database/key bundle is privately staged and published
  without overwriting. Restore accepts only new storage, starts no service, and
  never copies IPC. Interrupted, missing-half, mismatched-key, unsafe-permission,
  checksum, and existing-destination paths fail closed.

## Verification protocol

The machine-readable [manifest](DEL-05.json) binds scope, claims, five gates, and
a causal witness to the feature tree. Final gate results belong to the external
tree-bound attestation generated by the repository evidence verifier; this prose
is not a substitute for a successful final gate or merge approval.

```sh
# Activate the bootstrapped Python environment and pinned Node toolchain first.
make test-del-05-runtime
make test-del-05-backup
make test-del-05-tooling
make test-del-05-compose-backup
make verify-clean REF=HEAD
make verify-architecture
```

The first three gates use the current source explicitly on `PYTHONPATH`. This
also makes the witness execute its archived source, not the caller's editable
installation. The witness restores the pre-DEL-05 demo resume methods while
retaining the new worker and tests: expected failure is an admitted run failing
to complete, not a missing dependency/import or failed test setup.

The separate Compose backup gate builds the current requirement checkout into a
new scoped image and exercises source-volume backup, restore into new volumes,
second backup, all-table/key identity equality, and non-overwrite refusals. It
validates ownership before removing its temporary containers, image aliases,
four data/key volumes, and secret-bearing bundles. It never starts the app or
  uses a developer installation. This is distinct from the exact-export clean gate.

`verify-clean` uses Git to export only a selected commit. It refuses unsafe archive
members, environment files, remote daemons, unscoped names, host-bind mounts,
external volumes, unsupported network profiles, and unsafe cleanup targets.
Image/package acquisition is recorded separately from application/test execution.
After startup it inspects real container settings and loopback publication,
probes backend IP denial, checks `5/12/36/43` catalog counts and safe session modes,
quiesces writers for a whole-database zero-write reseed check, runs the five demos,
and exercises approval and real process restart/replay. Signed webhook and due
schedule fixtures preserve receipt/work/run/occurrence identities across restart.

Backend and frontend static/unit/integration suites run in prebuilt containers
with `--network none`. Frontend tools invoke their already installed binaries,
not an implicit package-manager install. Browser smoke runs against the production
web proxy, shares its network namespace, and blocks requests outside the exact
loopback origin, WebSockets, and service workers. Cleanup removes only validated
test containers, three volumes, network, and tracked export; reusable image/cache
  layers may remain. Caller-worktree state is checked separately and preserved.

Both Docker gates pin the effective local Unix daemon and its default builder,
including when a remote builder was previously selected. Internal deadlines leave
bounded cleanup time before the outer requirement timeout: clean execution/cleanup
`1620/120` seconds; backup execution/cleanup `420/150` seconds. Failure remains
failure if cleanup cannot confirm removal; unrelated resources are not removed.

## Residual risks and deferred delivery work

The tested Docker Desktop 29.7.2 discarded host publication on both internal/NAT
and internal/isolated bridges. Only the static web proxy therefore uses a normal
scoped NAT ingress network with a loopback-only published port. It retains an
OS-level external route; nginx has no external upstream or resolver. Backend
processes cannot use that route. This is not a claim that every container has an
OS egress firewall. Docker/filesystem administrators and the local self-approving
operator remain trusted.

Base images and application dependencies are pinned; acquisition may contact
public registries. OS packages/browser platform dependencies are acquired during
that phase, so bit-for-bit OS package reproducibility is not claimed. Real delivery,
public/multi-user authentication, hosted deployment, and production backup RPO/RTO
are not qualified. The complete documentation set, broader task-runner aggregation,
remaining CI hardening, and full 124-requirement acceptance remain separate rows.
