# ORCH-08 verification note

ORCH-08 now keeps every write-bearing plan paused behind one durable complete-set boundary. Write-plan persistence creates the plan, ordered steps, proposed external actions, approval requests, authorization-set members, and current-set head in the same transaction that moves the Run to `awaiting_approval` and each WRITE step to `awaiting_approval`. A partial decision is deliberately inert: one approved member creates no approval use, reservation, dispatch attempt, or connector call.

The boundary service reloads the current head, complete ordered membership, sealed requests and decisions, exact actions, parent Run, member steps, and full persisted plan before choosing an outcome. It validates each member's complete chain: the initial request, any expiry and renewal link, the selected current leaf, its decision or expiry, and the resulting boundary mutation. Exact expiry is evaluated before release. Only a complete fresh approved set can cross the barrier. The release transaction consumes every request once, writes one approval use and immutable reservation per member, transitions every action to `dispatch_reserved`, releases every WRITE step to `ready`, moves the Run to `executing`, records the released Run version and release hash, and appends the corresponding typed audit witnesses before one commit. Any persistence or audit fault rolls the whole release back.

Rejection and cancellation remain zero-call outcomes. One rejection closes the entire current set, rejects its action, supersedes and cancels still-actionable siblings, terminalizes the Run and plan steps, and creates no use or reservation. Exact expiry leaves the set paused and consumable by nobody; approved and pending leaves retain distinct, replay-validated expiry witnesses. When an authorization set contains initial and renewed generations, the first evaluation and every replay return only the selected current expired request IDs in stable membership order. A later rejection may close the action for an unchanged expired sibling without fabricating a request supersession, but replay still requires the removed generation's renewal witness. Pre-release cancellation closes every remaining member without consumption. Post-release cancellation changes the Run so the repository can no longer derive valid release authority for a future claim; it does not pretend that an already-sent provider request can be recalled.

The dispatcher no longer accepts a Run version as sufficient authority. Each claim and call-start requires an exact `ReleaseAuthority` reconstructed from the committed current-set head, membership and release hashes, approved decision, approval use, action reservation, released Run version, and persisted WRITE step. A first physical call atomically marks the durable attempt and transitions that reserved WRITE step from `ready` to `executing` before the connector is invoked outside the transaction. A provider-idempotent retry retains the prior committed call-start lineage and does not replay the step transition. Tampered decisions, forged release hashes, generic WRITE starts, stale parent state, and inconsistent retry lineage fail before another connector call.

Boundary and dispatch mutations have exact redacted witnesses. Release records `action.dispatch_reserved` and `approval.consumed` for every member alongside Run and Step transitions. Rejected or cancelled siblings use `approval.superseded` and `action.cancelled` only when the corresponding aggregate actually changes; an unchanged expired request receives no fabricated supersession event. Claim and call-start record `action.dispatch_claimed`, `action.call_started`, and the first-call Step transition. Released, closed, and still-open expired-set replay validates the full initial, renewed, current, and boundary member history and refuses to heal a deleted audit row, whether the expired current leaf previously carried an approval decision or remained pending.

The persistence model binds the current head, ordered members, approval uses, decisions, reservations, action hashes, release hashes, released Run version, and step identities with exact composite uniqueness and foreign keys. Fresh SQLite enables foreign keys and reports no violations after the exercised workflows. All mapped tables and the new constraint shapes compile for both SQLite and PostgreSQL dialects; PostgreSQL runtime execution is not part of this evidence.

Machine authority: `ORCH-08.json`. The gate runs the focused ORCH-08 boundary, storage, and audit suites without network access, then reruns the affected RUN-05 dispatch/recovery, RUN-08 approval persistence, RUN-10 decision, and ORCH-09 lifecycle/audit contracts. The connection witness restores the key boundary, dispatcher, and repository implementation paths and requires this gate to fail.

The evidence does not claim external-system atomicity, downstream exactly-once delivery, or general compensation. ORCH-08 proves release authority and a committed call-start; RUN-05 owns exact delivery replay, durable receipts, retry classification, and recovery after that point. Post-call cancellation is best effort, while reserved/claimed cleanup remains ORCH-06 and RUN-03 scope. The requester is still a free-string planning snapshot, and the stored decision authority is not a live revocation check. Semantic or membership change still fails closed with `full_set_epoch_required`; selecting and superseding a completely new epoch remains a later replan seam. There is no distinct authorization-set aggregate audit event or complete operator timeline yet; RUN-06 and AC-14 retain that scope. DEL-04 owns migrations, PostgreSQL runtime parity is unexecuted, and broader API, UI, and demo journeys remain future requirement work.
