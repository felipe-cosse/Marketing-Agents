# AC-10 — Identical webhook replay never duplicates work or execution

Status: verified by executable local public-API acceptance checks.

Requirement: `Identical webhook replay creates/executes no duplicate work.`
Plan 07 requires authenticated exact-byte receipt replay, one original work/run
per bound instance, stable resource links, collision rejection and no inline
execution. This acceptance adds end-to-end execution evidence to the existing
API-05 and RUN-04 admission, persistence and concurrency checks.

## Real-composition replay journeys

`tests/acceptance/test_ac_10_webhook_replay.py` uses fresh migrated/seeded SQLite,
the default runtime, real public configuration and approval routes, a nonproduction
HMAC secret, and real workers. Observation wrappers record entry and call the
original deterministic model/read/write implementations; no product response,
receipt, authorization, repository or provider result is stubbed.

Configuration is installed through session/CSRF-aware HTTP PATCH requests with
the current ETag. Runtime reconstruction loads the configured source registry.
The webhook body and signed timestamp are authenticated through the normal ASGI
route. Initial HTTP acceptance creates no plan, execution control, action, attempt
or artifact and invokes no provider. Every delivery is joined to its original
receipt, work, run, instance, configuration revision and exact admitted input.

### Model execution

One configured LinkedIn comment-replier instance receives one signed event.
Repeated delivery before execution, including after runtime reconstruction,
returns the identical receipt and resource links with only the disposition changed
to `replayed`. The real worker then completes exactly one model call, one first
successful attempt and one verified artifact linked to the original work/run,
step, instance, template, workflow, output schema and source request.

Replaying after completion and after another runtime reconstruction preserves
those records. Real worker passes are idle and no additional model, read or write
call, attempt or artifact appears.

### Approved two-instance fan-out

The same authenticated event is bound to two attendee-scheduler instances. It
creates one receipt with exactly two deliveries, distinct work IDs and distinct
run IDs. Replay is checked at admission, pending approval, authorized-but-not-yet-
executed, completed, and reconstructed-runtime stages.

Each real worker plan pauses with one exact attendee-enrollment action and pending
approval. There are no calls, reservations, attempts, receipts or artifacts before
approval. The original pending request IDs survive replay and reconstruction.
Real public approvals authorize each run; approval HTTP requests do not execute
the connector inline. Approval is per run, not an event-wide fan-out barrier.

After reconstruction, workers execute exactly two calls: one per original action.
Each observed proof joins to its immutable action/hash, request, decision, use,
reservation and idempotency key. Each action has one first successful dispatch
attempt and one matching durable receipt, with explicit mock/provider metadata
and `external_side_effect: false`. There are two decisions and two uses linked to
consumed requests, and no model calls or artifacts for these write-only workflows.

Postcompletion replay and changed-body rejection preserve all selected business
facts. Subsequent worker passes remain idle. A newly reconstructed connector
bundle has zero new in-memory mock inserts while the two original durable receipts
remain present; the test does not confuse a reset local counter with lost effects.

## Negative controls and recovery

- A wrong signing secret returns `401 webhook_authentication_failed` before any
  work or call. Edited raw bytes under the original signature are also rejected.
- Correctly signed changed content or whitespace-only body changes under the same
  source/event return `409 webhook_idempotency_conflict` without creating work.
  A changed attendee command is also rejected after the original effects complete.
- Pairing the database with a different installed digest key fails normal runtime
  startup with `database_unavailable`. Rebuilding with the untouched original key
  retains all business facts, returns the original replay outcome and successfully
  executes the original model run once.
- An isolated private-database fault changes only the stored receipt key-version.
  After reconstruction, replay returns sanitized `503 webhook_unavailable`,
  retaining the original received run with no plan, execution, action or effect.
  This is not a supported key-rotation operation and does not imply that already
  admitted valid work is cancelled; no worker is drained in this negative case.

All checked webhook responses are no-store, and errors do not reflect the signing
secret or signature. Exact snapshots cover receipt/delivery/work/run/transitions,
plan/steps, execution controls/policies/windows/attempts, artifacts, actions,
dispatch attempts, connector receipts, requests/decisions/uses, authorization
sets/heads/members and local key identity. They exclude all audit records,
session bookkeeping and worker leases; they do not assert an unchanged whole
database. Replay adds exactly the expected signature-validation and duplicate-
suppression webhook audits. Authenticated collision audits are asserted separately.

## Limits

New journeys exercise sequential replay with fresh-enough signatures and unchanged
source authority. Concurrent admission and signature freshness are supplementary
regression evidence, not new default-runtime race or stale-replay journeys. No new
mapper-drift or source-switch journey is claimed. Runtime reconstruction is in-
process against durable SQLite, not an OS-process crash. Selected tests do not
launch servers or child processes; socket-deny enforcement is Python-local, not
an OS network boundary. Deterministic mock call/receipt counts do not establish
real-provider delivery or universal exactly-once behavior. CI stays disabled.
