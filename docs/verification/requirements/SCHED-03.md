# SCHED-03 — Stable occurrence ID feeds run idempotency

SCHED-03 turns a claimed schedule's exact persisted due instant into a durable, versioned occurrence identity. The ID is a domain-separated canonical SHA-256 digest over only the schedule ID, scheduled UTC instant, and persisted recurrence-semantics version. Worker identity, lease times and version, processing time, payload, and mutable routing facts cannot change it. Each occurrence also records the original timezone, canonical local wall-clock representation, and selected fold without making those values part of the ID.

Schedules now persist their trusted workflow binding and recurrence-semantics version, and both fields are covered by the schedule consistency digest. Before ingress mutates anything, a no-op conditional update acquires a transaction-scoped fence over the complete active claim: schedule and due instant, owner, claim and expiry times, version, recurrence version, enabled state, and current digest. Exact expiry remains active; stale, replaced, future-clock, and strictly expired claims lose the fence.

The production occurrence-ingress service owns the schedule routing fields. It hard-sets `source="schedule"`, uses the derived occurrence ID as `event_id`, copies instance, trigger, and workflow only from the persisted schedule, and passes the resulting envelope through the configured `IncomingWorkValidator`. In one caller-owned unit of work it inserts or loads the claimed occurrence, calls `IdempotentWorkRunReceiptService.receive_in_uow(...)`, links the authoritative WorkItem and primary Run, verifies create/replay dispositions agree, and commits once. That existing receipt path retains Work source-key uniqueness, one primary Run per WorkItem, the initial Run transition, and its audit witness.

The occurrence table enforces a primary occurrence ID, unique `(schedule_id, scheduled_for_utc)`, unique WorkItem and Run links, restrictive foreign keys, complete state/link tuples, supported folds/states, and a consistency digest over the full row. Exact restart resubmission returns the same occurrence, WorkItem, and Run; changed input under that same stable event reaches the normal Work idempotency conflict. A fault after receipt creation but before occurrence linkage rolls the occurrence, WorkItem, Run, transition, and audit back together.

This evidence does not claim automatic recovery or exactly-once execution. SCHED-04 owns misfire detection and `skip` or `run_once`; SCHED-05 owns recurrence recomputation, next-run advancement, occurrence audit, and lease release in the larger atomic transaction; SCHED-06 owns expired-lease restart discovery and recovery races. The trusted caller still supplies mode, campaign-brief reference, instance configuration revision, and payload, all of which are revalidated. Runtime tests use file-backed SQLite; PostgreSQL DDL compiles, but PostgreSQL runtime contention, polling, APIs, authorization, migrations, metrics, and deployment remain outside this requirement.
