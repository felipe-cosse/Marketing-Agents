# SCHED-01 — Store original IANA timezone and next UTC run

SCHED-01 introduces one explicit recurrence boundary for initial schedule configuration. It accepts only the supported five-field cron profile and an exact IANA timezone key, preserves both values, and calculates the first strictly future aware UTC instant. The wall-clock resolver follows ADR-0008: a nonexistent spring-forward time advances to the first valid local instant after the gap, while an ambiguous fall-back time selects the earlier UTC fold once.

The configured Schedule is wired into the SQLAlchemy unit of work. Its original timezone key, cron, current next UTC run, misfire-policy enum, enabled state, and version persist as one row with a due-scan index. File-backed SQLite restart tests prove exact round-trip and exact create replay; compiled SQLite and PostgreSQL DDL prove the portable column, Boolean, timestamp-with-time-zone, constraint, and index shapes.

The boundary fails closed on unsupported or impossible cron expressions, unknown timezone keys, non-UTC calculation boundaries, and invalid adapter output. Initial persistence rejects changed create-time facts for an existing ID, rolls back uncommitted rows, and verifies a domain-separated consistency digest during hydration. The digest detects unrecomputed row drift; it is not a keyed authorization control against an administrator who can rewrite both the row and digest.

This evidence intentionally stops at initial configuration and storage. The low-level repository accepts an internally constructed validated Schedule, so provenance through the calculator is demonstrated through the connected service-to-UoW test rather than claimed universally. Leases and claims, occurrence IDs, runtime misfire behavior, transactional advancement, and recovery remain SCHED-02 through SCHED-06. PostgreSQL runtime rollout and migrations remain DEL-04. Public APIs, authorization, observability, preview, and the worker loop remain later requirement scope. Machine authority: [`SCHED-01.json`](SCHED-01.json).
